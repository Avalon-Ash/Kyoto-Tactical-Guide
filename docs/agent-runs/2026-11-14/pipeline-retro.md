# 夜間重構流水線檢討與改進計畫（2026-11-14）

撰寫：主代理（Claude Opus 5.5）。對象：`C:\Git\_wt_kyoto_rebuild\.claude\dispatch\night.sh` 與它的規則檔。

## 結論

一晚上 p1 過、p2 連四次加 Argon 兩次失敗、p3 兩次失敗。逐條對過紀錄，**主因幾乎都在主代理設計的流水線與規則，不在 Astra 或 agy 的能力**：

- 規則互相矛盾，派工單把需要改的檔案鎖死，一包範圍過大，導致實作代理做不完。
- 流水線沒保存證據、截斷輸出，導致審查者只能判 FAIL。
- 退回時刪掉新檔，導致每次重試都從零開始。
- 換更大的模型沒有帶新假設，導致 Argon 一包燒光一週額度。

Astra 的設計與審查是一致而且正確的：它指出的問題（瓦線、接點、證據、測試衝突）都真實存在，其中好幾條本來應該由整合者（主代理）解決。

## 改進計畫

### A. 規則只有一份，範圍圍欄和行為測試要分開

- 規則合併成一份，agy-rules 和 review.md 共用同一段「硬條件」文字；不准一份放寬、另一份不放。
- 測試分兩類並在檔內標註：
  - **行為測試**：永遠不准改。
  - **範圍圍欄**（例如「尚未遷移」）：由下一包負責更新，更新方式寫在設計裡。
- 判斷是否違規看標註，不看「有沒有動到既有測試」。

### B. 架構決定交給設計者，整合衝突由主代理事先拍板

- 派工單的 write set 由 Astra 依設計需要列出，可以包含公共檔案。主代理只禁止真正危險的東西：依賴、資料 schema、受保護檔案。
- 審查者遇到「需要整合者決定」的問題，回 `BLOCKED` 而不是 `FAIL`。流水線收到 `BLOCKED` 就停在那包並通知主代理，不再重試，也不換模型。

### C. 證據由流水線產生，不靠代理自述

gate 要產出以下證據：

- 完整 diff，含新檔（先 `git add -N`，或另外打包新檔）。
- 測試與 lint 的完整輸出。
- 全部鏡頭：原始 jobs 加上代理追加的鏡頭，**不覆蓋、不截斷**。
- 每張截圖的時間與 dataset。

審查單只看 gate 產物。

### D. 不毀掉工作

- 退回前先把整個工作樹打包（已加：`pkg-<id>-new-<n>.tgz`）。
- 判定為「可修」的 FAIL，下一次從上一次的工作樹接著改，不還原。
- 只有判定方向錯誤才還原。

### E. 額度與時限

- 每次 agy／Codex 呼叫都有 `timeout`（已加：agy 5400 秒）。
- 開跑前用一行 prompt 探一次額度。
- 429 或 `RESOURCE_EXHAUSTED` 不算嘗試，立刻停下並記進 `QUOTA.md`。

### F. 包要小

每包最多 2 個 builder 或 1 個區域性主題；p2 這種範圍拆成 3 包：

1. 屋殼與瓦。
2. 牆與塔。
3. 門與迴廊。

### B2. 合約不合理就提案修改

設計者或審查者指出某條合約（AGENTS.md、派工單、規則檔）讓架構不合理時，主代理寫一段修改提案（哪一條、為什麼、改成什麼、回退方式）交使用者決定，而不是繼續在原限制下重試。

### G. 升級要有新假設

模型升級前必須在 log 寫出「上次失敗的原因」和「這次改了什麼條件」。條件沒變就不升級，回主代理處理。

### H. 先乾跑

改過流水線後，先用一個只改註解的假包跑一輪全流程，確認：

- packages 讀得到。
- gate 證據齊全。
- 審查讀得到證據。
- 退回能保住新檔。

確認後才放夜間長跑。
