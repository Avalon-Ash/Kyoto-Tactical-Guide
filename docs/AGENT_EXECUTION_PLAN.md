## 2. 建議模型與強度

以下為派工設定表。使用者已授權 Phase 0／1、Phase 2 與 Phase 3 依表指定模型／強度；實際工具請求與限制見執行紀錄。未獲使用者明確指定不同模型時，子代理依目前工具規則沿用主代理模型，不擅自套用表中的模型 override。
本次不建立 `.codex/config.toml`，不覆寫主代理或使用者全域模型偏好。

| 角色 | 任務類型 | 建議模型／強度 | 範圍與限制 |
|---|---|---|---|
| explorer | 定位符號、查引用、找已知差異 | gpt-6-luna／low | 只讀；先精確搜尋，最多兩輪擴大搜尋；找不到就回報 |
| worker | 確定性的標籤／locale 編輯、指定命令驗證 | gpt-6-luna／medium | 每包最多 3 個指定檔案；不得自行做地理或分類決策 |
| researcher | 地標座標、行政區身分、來源交叉核對 | gpt-6.1-sol／medium | 網路與程式只讀；交付來源、日期、候選座標、確信程度 |
| implementer | 界線明確的跨函式實作，例如 loader、投影工具 | gpt-6.1-sol／medium | 指定 write set；不得擴張到整體架構 |
| reviewer | 完成 diff 的獨立審查、回歸情境 | gpt-6.1-sol／medium | 只讀；按指定 base SHA 比較，不能只信代理報告 |
| specialist | 已有證據的座標／React 生命週期疑難 | gpt-6.1-sol／high | 一個問題一包；先記錄失敗原因與升級理由 |
| 主代理 | 分解、核心地圖整合、美術取捨、最終驗收 | 保留使用者設定；一般 medium，複雜整合建議 high | 強度建議不代表主代理已自行切換模型 |

- 平常不使用 Astra、xhigh、max、ultra。確實需要時先提交問題、已嘗試方法與升級理由，取得對應模型／強度的使用者指示；不是每個任務都要再問一次。
- 高強度不能補足無來源資料；來源不足標為阻塞，不以更換模型推測答案。
- 最多兩個子代理同時工作，機械任務只有幾行時主代理直接完成。禁止子代理遞迴派工。
- 這是本專案成本與風險配置，並非對不同模型能力或用量的官方保證。

## 4. 工作包與同時寫入規則

- Phase 0–1：最多一個資料 worker 加一個只讀 researcher。主代理不寫 worker 正在編輯的檔案；資料按 T 順序驗收，不能把 T1.1 與 T1.2 互相依賴的修改同時交付。
- Phase 2：最多一個有明確 write set 的 implementer 加一個 reviewer／researcher。若主代理下一步就依賴其結果，主代理自行做，不為了開代理而等待。
- Phase 3：美術由主代理統一寫入。幾何工具可先委派；審查者只讀已完成版本，不操作主代理正在使用的瀏覽器。
- 在開始前記錄 owner 表：任務、代理 ID、工作區、base SHA、可寫檔案、狀態。表放在該輪 `docs/agent-runs/<round>.md`；現在不建立虛構的執行紀錄。
- 子代理提交未 commit diff。主代理檢查來源與差異、整合、跑完整驗收、依授權 commit。一個 T 任務可以有多個小派工包，但不因此產生混合任務的 commit。
- 不和 Gemini 對同一 checkout 同時寫入。若使用者仍選 Gemini，這些角色可作為它的任務類型，不能宣稱已由本機工具啟動 Gemini。

## 5. 啟動前修正與停止點

1. T1.1 的 UK-075 警告允許延至 T1.2；精確警告清單比只看總數更重要。
2. T1.3 先查實際 locale 名稱再對座標，附來源。峰定寺、常照皇寺未核實時不得採用計畫估計值宣稱通過。單純已有國寶標籤也不能當作該標籤正確的證據。
3. T2.2 抓取腳本核對回傳行政區身分、合理範圍、幾何完整性與授權，不只取第一個 relation；遵守供應服務當時政策。
4. T3.2 市中心裁切是藝術版面，不聲稱完整行政區全圖；保留所有 11 區入口。手機點不到時調整命中範圍或提供可操作的區域清單，不以縮小字體作為唯一解法。
5. 程式片段是實作參考；允許在指定範圍修正型別、生命週期及平台語法，需記錄理由。功能範圍或資料決策變更則交主代理處理。
6. Windows 終端用 PowerShell 語法；例如環境變數用 `$env:GEO_THRESHOLD = '0.001'`，不照抄 Bash 的前綴賦值。
7. 每輪到 Phase 1、Phase 2、Phase 3 結尾交付一次完整驗收。使用者只授權某一輪時，不越界開始下一輪。

## 6. 回報與費用界線

- 派工前公布角色、指定或繼承的模型／強度、工作包及理由；不要把繼承設定說成已確認的特定模型。
- 任務兩次失敗後不繼續燒額度；交主代理縮小問題。未完成的必要查核或視覺驗收列為未完成。
- 審查以確切錯誤、重現條件和檔案位置為準，不做無限多輪「再審一次」。新修改影響哪些證據，只重驗相關部分及必要整合檢查。
- 合約與 Markdown 不會自動鎖模型或阻擋指令。Phase 2／3 依表派工，未建立模型設定檔；若之後要可載入的 `.codex/agents/*.toml`，須按核准模型表另行落地與驗證，不能宣稱現在已生效。
